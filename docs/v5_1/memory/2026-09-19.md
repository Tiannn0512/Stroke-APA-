## ⚠ 勘误：M4 失败根因不是（只是）内存竞争，而是脚本转置 bug

- 09-18 审计我写下"M4 四次失败真因确定 = 内存竞争"——**该结论错误**。09-19 第 6 次尝试在干净内存窗口复跑，暴露真实根因：`scripts/p3_m4_reference_sets.py` 的 Set 1（GSE74456）与 Set 3（GSE263986 zones）把计数矩阵按**基因×样本**直接传给 pydeseq2（缺 `.T`，pydeseq2 要求样本×行）。
- 后果链：Powell 优化器把 41,393 个基因当样本 → `eye(41393)` 申请 12.8GB → 报内存错误。**内存报错是表象**：即使内存充足，设计矩阵也退化了（Set 1 所有基因的 condition 被判成 "PAPTRAP"，因为基因名不以 Ctx 开头）——即使跑通也是废表。
- 09-17/18 的三次 OOM 属真实内存竞争（vmmem 挤压），但即使躲过 OOM 也会死在 eye() 分配或产出废表。
- **修复（09-19）**：Set 1 加 `.T` + 断言 6 行样本 + 断言 condition 集合 = {CtxTRAP, PAPTRAP}；Set 3 转置 + 断言样本数与 condition 集合。第 7 次尝试运行中。
- **教训（升级原教训）**：内存类报错必须区分"分配量级是否合理"——`eye(41393)` 这种 O(samples²) 分配本身就是维度错的铁证；pydeseq2 输入方向要用 `assert n_samples` 挡在拟合前。我的 09-18 日志审计只验证了"有内存压力"就定了根因，没追 allocation 形状——审计也要打到数字本身。
